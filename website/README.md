# GR Hotels website

The public website and content admin for GR Hotels: eight hotels and pubs with rooms across Britain.

- **Framework:** Next.js 16 (App Router, TypeScript) with Payload CMS 3 in the same app. Admin at `/admin`.
- **Database:** Supabase Postgres. **Media:** Supabase Storage via the S3 adapter.
- **Styling:** Tailwind CSS 4 with the Group Retreats brand tokens as CSS variables.
- **Hosting:** Vercel (one repository, one deployment). Root directory: `website/`.

Plain-English guides live alongside this file: `MANAGER-GUIDE.md` for hotel managers and `LAUNCH-CHECKLIST.md` for go-live.

## 1. Run it locally

You need Node 22 or newer, pnpm 10, and a Postgres database (local, or the Supabase project).

```bash
cd website
pnpm install
cp .env.example .env        # then fill in DATABASE_URL and PAYLOAD_SECRET at minimum
pnpm seed                   # creates tables, an admin user and placeholder content
pnpm dev                    # http://localhost:3000  and  http://localhost:3000/admin
```

Useful commands:

| Command | What it does |
|---|---|
| `pnpm dev` | Development server with hot reload. Database schema is pushed automatically. |
| `pnpm build` then `pnpm start` | Production build and server, as Vercel runs it. |
| `pnpm seed` | Adds or refreshes placeholder content. Safe to re-run. `pnpm seed -- --reset` wipes content first. |
| `pnpm generate:types` | Regenerates `src/payload-types.ts` after changing collections. |
| `pnpm migrate:create` | Writes a migration after a schema change (see Deploy). |
| `pnpm migrate` | Applies pending migrations to `DATABASE_URL`. |
| `pnpm typecheck` / `pnpm lint` | Checks run before every push. |
| `pnpm test:redirects <url>` | Checks every old grhotels.co.uk URL against a deployment. |
| `node scripts/screenshots.mjs <url> <dir>` | Phone and desktop screenshots of key pages. |
| `node scripts/admin-check.mjs <url> <dir>` | Logs in as admin and manager and checks what each can see. |

Without `RESEND_API_KEY` or SMTP settings, emails are printed to the terminal instead of sent. Without Turnstile keys the spam check is skipped. Without HubSpot IDs newsletter sign-ups are logged, not forwarded.

## 2. Project layout

```
website/
  src/
    payload.config.ts       Payload setup: collections, globals, plugins, email, storage
    collections/            Hotels, Rooms, Menus, Events, Offers, Pages, Media, Testimonials, Enquiries, Users
    globals/                Site settings, Navigation & footer, Announcement bar
    blocks/                 One folder per page-builder block: config.ts (admin fields) + Component.tsx (public render)
    access/                 Role rules: Admin sees everything, Hotel Manager sees only assigned hotels
    fields/                 Reusable fields: slug, link, block style, SEO tab, rich-text editors
    app/(frontend)/         Public routes, layout, API routes (enquiry, newsletter, book-targets)
    app/(payload)/          Admin and REST API (generated by Payload)
    components/             Header, footer, Book Now, forms, cards, cookie consent, admin dashboard
    seed/                   Placeholder content and the seed runner
    migrations/             Database migrations (generated)
  scripts/                  Redirect test, screenshots, admin smoke test
  vercel.json               Build command runs migrations before building
```

### How content is modelled

- **Hotels** own everything else. Rooms, Menus, Events, Offers and Testimonials each point at a hotel. Hotel Managers are assigned hotels on their user record and can only see and edit rows for those hotels (enforced in `src/access/roles.ts` and `src/hooks/enforceHotelScope.ts`, not just hidden in the UI).
- **Pages** and hotel pages are built from **blocks**. Editors choose a background tone, spacing and alignment per block. There are no free colour or font controls.
- **Dates drive visibility.** Menus show between "valid from" and "valid to". Events hide once they have ended. Offers show between their start and end dates. All of this happens at request time in `src/utilities/data.ts`; nothing needs unpublishing by hand.
- **Book Now** uses each hotel's `bookingUrl`. UTM tags are appended and a `book_now_click` event is pushed to the GTM data layer. With no URL set, the button falls back to the hotel phone number, then the enquiry form. On group pages it opens the hotel picker.
- **SEO** lives in a tab on every page and hotel. Blank fields fall back to sensible defaults in `src/utilities/generateMeta.ts`. `sitemap.xml`, `robots.txt`, Hotel/LocalBusiness and FAQ JSON-LD are generated automatically.

## 3. Deploy to Vercel

1. In Vercel, **Add New Project**, import this GitHub repository and set **Root Directory** to `website`.
2. Framework preset: Next.js. Build settings are read from `vercel.json` (install, then `pnpm migrate && pnpm build`).
3. Add the environment variables from `.env.example` under **Settings → Environment Variables** (Production and Preview). The important ones:
   - `DATABASE_URL`: the Supabase **transaction pooler** string (port 6543) with `?sslmode=require`.
   - `PAYLOAD_SECRET`, `PREVIEW_SECRET`: long random strings.
   - `NEXT_PUBLIC_SERVER_URL`: `https://www.grhotels.co.uk` in Production; leave blank in Preview so Vercel's URL is used.
   - `S3_*`: Supabase Storage S3 keys (Project Settings → Storage → S3 access keys). Create a bucket called `media` and make it public.
   - Email, Turnstile, HubSpot and GTM values as they become available.
4. Deploy. The first deploy runs the migrations and creates the tables. Then either run `pnpm seed` locally against the production `DATABASE_URL`, or log in to `/admin` and create the first user.

### Schema changes

Locally the schema is pushed automatically in dev. For production, generate a migration and commit it:

```bash
pnpm migrate:create   # writes src/migrations/<timestamp>_*.ts
git add src/migrations && git commit -m "Add migration for ..."
```

Vercel applies it on the next deploy. Never edit a migration that has already been deployed.

### Preview deployments

Every branch gets a preview URL from Vercel. Previews use the same database unless you point `DATABASE_URL` at a Supabase branch. `robots.txt` blocks search engines on anything that is not the production deployment.

## 4. Back up and restore

**Database.** Supabase Pro takes daily backups automatically (Project Settings → Database → Backups) and supports point-in-time recovery. For an on-demand copy:

```bash
pg_dump "$DATABASE_URL" --no-owner --format=custom --file=grhotels-$(date +%F).dump
pg_restore --clean --no-owner --dbname "$DATABASE_URL" grhotels-YYYY-MM-DD.dump
```

**Media.** Files live in the Supabase Storage bucket `media`. Download a copy with any S3 client using the same keys as the site, for example `aws s3 sync s3://media ./media-backup --endpoint-url "$S3_ENDPOINT"`.

**Content versions.** Every hotel, page, room, menu, event and offer keeps up to 50 versions in the admin. Open the document, choose **Versions**, pick one and **Restore**. Deleted documents are not kept; restore those from a database backup.

## 5. Roles

| | Admin | Hotel Manager |
|---|---|---|
| Hotels | All, every field | Assigned hotels only. Cannot change name, web address, booking link, enquiry email or display order |
| Rooms, menus, events, offers, reviews | All | Assigned hotels only |
| Enquiries | All | Assigned hotels only |
| Images & files | All | Can upload; can edit or delete only their own uploads |
| Pages, navigation, site settings, redirects, users | Yes | Hidden and blocked |

Create managers under **Users**: set role to Hotel Manager and tick their hotels. They receive a password-reset link by email if you leave the password blank and use "Forgot password" on the login page.
